# 模型切换后 DSH 对话失败与恢复

## 本轮原因

本次日志不同于11月15日的空助手摘要400：后续请求均在DSH路径返回 `stop unconfirmed; restart required`。只读核查发现本机DSH宿主进程不存在，桥接健康接口无法连接；默认模型（包括显式选择站点主模型）按已有配置走DSH，未映射模型仍走原API。因此切回默认模型会遇到执行服务故障，与Haiku摘要修复不同。

已使用现有 `/home/ubuntu/.local/bin/dsh-web` 恢复原Web profile。未升级DSH、安装服务、改监听/配置/凭据或开机策略。恢复后认证健康接口返回protocol=1、active=0、hostRunning=0。此事实不能证明此前进程退出的原因，不将其推断为模型提供商错误。

## 修复

- 保留原串行gate、工具取消/等待退出、审批与故障锁定。锁定时记录原请求ID。
- 后续新请求先对原ID发幂等取消；只在经过认证的桥接返回 `stopped:true` 后解除锁定并生成全新请求ID。健康检查成功不能代替取消确认；503、错误/缺失确认继续阻止。
- 原桥接的取消接口同时退役未知ID，拒绝该ID的晚到提交。不会重新提交旧任务、重放已执行工具、静默切引擎或回滚已有动作。
- 服务离线与未确认停止向用户分别说明，不再笼统提示模型调用失败。服务端日志记录实际DSH模型、提供商与选择器，便于区分模型与执行通道。

宿主本身仍由已有tmux启动流程管理，本修复不负责自动启动DSH或改变开机自启；服务恢复后不再必须通过重启MineAgent才能解除这个保护锁。

## 验证

`go test` / `go vet`：dshbridge、agent、qq、body、config；`go test -race`：dshbridge、agent；`node --test dsh-bridge/server.test.mjs` 均通过。

新增覆盖：旧停止确认失败时新请求不进入；只有对同一旧ID确认后才能提交新模型与新ID；工具只执行一次；宿主离线后恢复，先取消确认再接受新请求。原有审批身份、局部工具退出、串行与等待取消、未知ID退役等断言保留。

真实安装版DSH用独立临时profile和假模型通过：历史、思考强度、图像、作用域工具、原生工具拒绝、取消后继续与轮次预算。真实运行宿主另用一次合成文本、零工具验证默认模型成功，约2.805秒；未使用真实聊天正文，也未向QQ投递测试消息。
